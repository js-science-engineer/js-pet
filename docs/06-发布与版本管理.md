# 发布与版本管理

## 一、版本号规则

采用语义化版本 `主版本.次版本.修订号`（MAJOR.MINOR.PATCH）：

| 变化 | 何时递增 | 例子 |
|---|---|---|
| **MAJOR** | 数据结构不兼容、需要用户手动迁移 | 1.0.0 → 2.0.0 |
| **MINOR** | 新增功能，向后兼容 | 0.1.0 → 0.2.0（自动更新、云同步） |
| **PATCH** | 只修缺陷，不改行为 | 0.1.0 → 0.1.1（修拖动、修打包） |

改版本号要同步这三处：

1. `package.json` 的 `"version"`
2. `CHANGELOG.md`（新增一节，写清"新增 / 修复 / 已知问题"）
3. 打 git tag：`git tag v0.2.0 && git push origin v0.2.0`

## 二、为什么二进制不放进版本库

安装包单个约 114MB，**超过 GitHub 单文件 100MB 的硬限制**，直接提交会被拒绝。
所以：

- 版本库只放**源码 + 文档 + 构建期素材**
- 安装包放到 **GitHub Releases**（每个 release 支持上传多个附件，单文件上限 2GB）
- `releases/vX.Y.Z/bin/` 在 `.gitignore` 里被忽略，只作为**本机的暂存目录**，
  方便你上传前把产物集中到一起

## 三、发布一个新版本的完整流程

### 1. 改版本号与日志

```bash
# 修改 package.json 的 version
# 在 CHANGELOG.md 顶部新增一节
```

### 2. 跑全量回归（必做）

```bash
npm test        # 单元测试，必须全绿
npm run smoke   # Electron 冒烟自检，必须 SMOKE_OK
```

### 3. 打包

```bash
# Windows
ELECTRON_MIRROR=https://npmmirror.com/mirrors/electron/ npm run build:win

# macOS（必须在 Mac 上）
npm run build:mac
```

### 4. 验证打包版（重要）

```bash
# 免安装目录版直接冒烟，检查结果文件
JS_PET_SMOKE=1 ./dist/win-unpacked/js-pet.exe
cat "$APPDATA/js-pet/smoke-result.json"     # 期望 "ok": true

# 检查包内是否混入了不该进的东西（测试代码 / 构建工具 / 绿幕原图）
npx asar list dist/win-unpacked/resources/app.asar | grep -E "tests/|tools/|raw2|pet-demo" 
```

真机人工复检清单（发布前建议过一遍）：见 [TODO.md](../TODO.md)。

### 5. 归档产物到本机暂存目录

```bash
mkdir -p releases/v0.1.0/bin          # 换成实际版本号
cp dist/js-pet-0.1.0-setup.exe dist/js-pet-0.1.0-portable.exe releases/v0.1.0/bin/
```

### 6. 提交源码并打标签

```bash
git add -A
git commit -m "发布 v0.1.0：<一句话说明>"
git tag v0.1.0
git push origin main --tags
```

### 7. 创建 GitHub Release

1. 打开仓库页面 → **Releases** → **Draft a new release**
2. **Choose a tag** 选刚推上去的 `v0.1.0`
3. 标题填 `v0.1.0`
4. 说明正文直接**粘贴 `CHANGELOG.md` 里对应版本的那一节**，
   或粘贴 `releases/v0.1.0/RELEASE-NOTES.md` 的内容
5. **Attach binaries** 上传安装包（从 `releases/vX.Y.Z/bin/` 里选）：
   - `js-pet-0.1.0-setup.exe`
   - `js-pet-0.1.0-portable.exe`
   - `js-pet-0.1.0-arm64.dmg` / `-x64.dmg`（在 Mac 上构建后上传）
6. 点击 **Publish release**

### 8. 发布后自检

- [ ] Releases 页面能正常下载，文件名与文档里写的一致
- [ ] 下载后安装、启动、看到宠物
- [ ] README 里的版本号与下载说明已同步

## 四、发布渠道说明

当前策略是**手动分发**（"精简上线"）：

| 项目 | 现状 |
|---|---|
| 自动更新 | 未启用（下一版候选功能）。因此 `dist/*.blockmap` 暂时可以不上传 |
| 代码签名 | Windows 未签名（会触发 SmartScreen 提示）；macOS 未签名未公证（需用户放行一次） |
| 分发方式 | GitHub Releases 手动上传，或直接把安装包发给朋友 |

未签名的影响与处理写在 [Windows 安装](01-安装-Windows.md) 与
[macOS 安装](02-安装-macOS.md) 里，用户看到提示不会慌。

## 五、版本目录约定

```
releases/
├── README.md                    上传说明（本目录的入口）
├── v0.1.0/
│   ├── RELEASE-NOTES.md         该版本的发布说明（对应 CHANGELOG 的一节）
│   └── bin/                     本机暂存的安装包（不提交，仅用于上传）
└── v0.2.0/                      未来版本同样格式
    ├── RELEASE-NOTES.md
    └── bin/
```

## 六、以后想启用自动更新

1. 在 `package.json` 加 `electron-updater`，主进程在启动后调用 `autoUpdater.checkForUpdates()`
2. 在 `electron-builder.yml` 里配置 `publish`（GitHub provider）
3. 打包时会自动生成 `latest.yml` 等元数据文件，需要一起上传到 Release
4. 注意：未签名的情况下自动更新在 macOS 上会被 Gatekeeper 拦下，
   建议先解决签名再开自动更新
